SPAWN.md is a workflow template for projects where autonomous agents write most of the code and a human operator steers through bounded grants rather than step-by-step supervision. It is entirely Markdown files and a single JSON seed — no runtime, no framework, nothing to install.

Why it exists

Four questions nobody wrote down

Agentically built projects tend to fail on four questions. SPAWN.md gives each one a track with explicit rules, templates, and verification hooks. Pick a question.

Architecture track arch/

Design decisions are recorded as numbered improvement proposals with an EIP-style lifecycle and relationship headers (Supersedes, Requires, Extended-By). Final proposals are immutable; changes happen by supersession or by dated, explicitly bounded amendments. Decision history is append-only by construction.

Implementation state is kept out of the proposals. A separate machine-readable conformance map (arch/conformance.json) records per proposal whether the code conforms, which modules and tests satisfy it, and what gaps remain. Conformant entries require tests; partial entries require listed gaps; the map is updated in the same commit as the code it describes.

See the decision lifecycle ↓

Experiment track experiments/

Every contact with reality — paid runs, benchmarks, canaries, user tests — gets a numbered record declared before any spend: hypothesis with an explicit production mechanism, frozen scope, alternatives, risks, falsifiable acceptance criteria, and budget. Every record ends with a mandatory terminal closure: outcome, root cause, actual cost, next action.

Hard-won defaults: a complete zero-cost rehearsal before real dispatch (including the final publication and settlement steps), single-unit failures settle their unit rather than killing the campaign, terminally closed experiments are never resumed, and negative results are retained with the same care as wins.

Governance track governance/

Operator control is expressed as a charter: a falsifiable definition of done, autonomy grants (spend caps, decision scope), hard invariants whose violation voids the charter, direction constraints that encode already-diagnosed failure vectors, escalation triggers, and a reporting cadence in which prolonged silence is itself an anomaly. Inside the grants the agent does not ask permission; outside them it stops.

The track includes SELF-CORRECTION.md, a distilled failure playbook copied verbatim into every instantiated project.

Session lifecycle GOAL.md + experiments/HANDOFF.md

Missions are handed to fresh agent sessions through two documents with distinct authority: GOAL.md is normative (ordered deliverables, binding rules, budget, an explicit stop boundary) and HANDOFF.md is descriptive (verified current state, working conventions, known quirks, and a growing list of paid-for lessons). Sessions verify claimed state before relying on it, and rewrite the handoff for their successor when a mission completes.

The architecture track

A decision's life

Proposals are pure design documents — they record what was decided and why, never whether the code currently conforms. Step through the lifecycle.

Draft

Under active design. The proposal's Specification section uses MUST/SHOULD/MAY language and must be checkable — a proposal that cannot be tested cannot be tracked.

  • conformant code and tests match the spec — requires listed tests
  • partial known gaps — requires listed gaps
  • unimplemented accepted design, no code yet
  • n-a process/meta proposal with no code surface

Updated in the same commit as the code that changes conformance. A checker script validates the map — no dangling file references, no missing entries — and runs in the standard verification set.

The session lifecycle

Every session starts cold — by design

Fresh sessions are a feature, not a bug: the workflow makes a cold start safe. The mission file is what a session actually keeps in working memory.

  1. Read GOAL.md, then experiments/HANDOFF.md, then the charter.
  2. Verify the claimed current state — run the verification commands, check conformance. The handoff says “verify before relying” and means it.
  3. Read the specific proposals the mission names, in full, before designing.
  1. Architecture-track decision → proposal first, accepted, then code. This is what lets parallel worker sessions build against a stable contract.
  2. Semantic commits, bounded size — reviewable in one sitting, roughly ≤ 800 changed lines.
  3. Independent review before irreversible or paid steps, where available.
  4. Full verification gates green before any real-world dispatch.
  5. Report at every deliverable completion and every terminal closure — compact: outcome, root cause, totals, next action. Prolonged silence is itself a report-worthy anomaly.
  1. Update conformance, close experiment records, regenerate derived docs via their generators — never hand-edit generated files.
  2. Rewrite experiments/HANDOFF.md for the successor.
  3. Update GOAL.md or mark it complete; STOP at the mission boundary even if momentum suggests continuing — follow-on work is a new mission.

The self-correction playbook

Ten distilled failure lessons from a real agentic project's history — most cost actual money or weeks. Read them when an experiment dies terminally, a failure repeats under a different guise, or the deliverable has not moved while the repo has.

1When a failure repeats with a new mask, question the assumption
After TWO terminal failures that rhyme, you are not allowed a third attempt at the mask level. Write down the assumption both attempts shared, construct the cheapest test that could falsify it, and run that instead. One philosophy error was “fixed” four times under different masks — killing four consecutive campaigns.
2Ceremony is not the deliverable
Agents under uncertainty drift toward building process — more validation, more lifecycle states, more tests of tests. Before adding machinery, name the recorded blocker that requires it. No blocker on record, no machinery.
3Don't gate stochastic processes on exact content
Any check of the form “the model output must equal exactly X” is a time bomb. Validate rates, structure, bands, and machine-checkable outcomes — exit codes, passing tests, schema validity.
4Per-unit failure is data, not death
A failed unit settles its own unit and gets its cause recorded; the campaign continues. Campaigns terminate on budget, a pre-declared failure-rate threshold (default >25%), or a hard-invariant hit — never on a single unlucky unit. No silent retries, no complete-case subset selection.
5Rehearse the LAST steps, not just the core
Multiple campaigns executed their expensive core perfectly and then died in unrehearsed publication or settlement stages, wasting the spend. A zero-cost end-to-end rehearsal of the complete path is mandatory before real dispatch.
6Attribute wins to declared mechanisms only
If the treatment won but not through the mechanism you pre-declared, you have an observation, not a result. Never re-narrate a lucky path as the designed win — the record's future readers can't tell the difference, which is exactly the problem.
7Claims and evidence are different substances
Anything the system says about itself is a claim. Evidence is a runner-executed gate, an externally reported actual, or a regenerable artifact. Label the two differently everywhere; never let a claim flow into a headline number.
8Losses are deliverables
An honestly measured loss defines the prize for the next cycle. Deleting negative results, resuming terminally closed experiments, or iterating past the mission boundary to turn a loss into a win are all the same corruption.
9Freeze what you compare against
Comparisons are only meaningful when scope is frozen. Discovering mid-flight that something varied silently doesn't downgrade the result — it terminates it. Diffs between successive plans beat re-freezing from scratch.
10The handoff is part of the work
A mission is not done when the code works; it is done when a fresh session can verify the state and continue without inheriting myths. Assume your successor knows nothing and trusts nothing — because the good ones don't.

Adaptation instead of variants

Seven bindings, derived — not chosen from a menu

There are no per-project-type editions. ADAPTATION.md defines seven bindings an instantiating agent derives from the project's own description, and records in the instantiated OVERVIEW.md.

B1

Proposal identity

A short prefix from the project name, zero-padded 4-digit numbering. Proposal 0000 is always the template itself.

B2

Architecture-track threshold

“Would two parallel sessions build incompatible things without this written down?” or “would reversing this cost more than a day?”

B3

Experiment & spend unit

Anything learned from reality rather than the test suite — provider dollars, CI minutes, user sessions, or wall-clock days.

B4

Verification set

Concrete commands from the project's stack: test runner, static checks, conformance checker, build. The set only grows.

B5

Charter thresholds

Total budget, per-experiment cap, consecutive-failure trigger (2 is a good default), failure-rate abort (>25%), reporting cadence.

B6

Generated artifacts

Every generator-owned file is marked “never hand-edit”, with its regeneration command named next to it.

B7

Holdouts

Reserve at least one evaluation surface that day-to-day iteration must not touch. Optimizing against your only validation surface is training on the test set.

Right-sizing: collapse documents, never drop the four questions

Tiny project: charter and GOAL.md can be one file; experiments one file; conformance a table. Keep proposal immutability and terminal closure — they cost nothing and are load-bearing. Medium: the full tree as given. Large: split handoffs per workstream; charters may nest, but hard invariants only ever tighten downward, never loosen.

The operator will reject: ceremony the project cannot feed · proposals written after the code as documentation theater · deleted failure records to look tidy. The failure history is the value.

Getting started

Point an agent at the repo

Give an agent this repository and a project description, and instruct it to instantiate the workflow. It commits the instantiated workflow before any product code.

  1. 1
    It reads WORKFLOW.md (the durable rules) and ADAPTATION.md (the derivation guide).
  2. 2
    It derives the project-specific bindings and records them in the instantiated OVERVIEW.md.
  3. 3
    It copies the tree, renames *.template.md files to their real names, fills every placeholder, and seeds the conformance map.
  4. 4
    It commits the instantiated workflow — Instantiate agentic workflow (from SPAWN.md) — before any product code.

Starter prompt 

Read WORKFLOW.md and ADAPTATION.md in this repository, then instantiate the workflow for my project: <describe your project>. Derive the seven bindings, copy the tree, fill every placeholder, seed arch/conformance.json, and commit the instantiated workflow before writing any product code.
